دليل نظام مستشفى النبض التخصصي

هذا الدليل يشرح كيف بُني النظام فعليًا: البنية، مصادر البيانات، منطق كل قسم، والمصطلحات التقنية المستعملة. كل معلومة فيه مستخرجة من الكود نفسه — أسماء الملفات والدوال المذكورة موجودة حرفيًا في المشروع.

هذا الملف مستقل عن الموقع. ليس صفحة من صفحات النظام ولا رابط له في القائمة — يُفتح لوحده مباشرة، ولا يستورد أي ملف من المشروع.

١ · نظرة عامة والبنية

النظام Multi-Page Application (MPA) — تطبيق متعدد الصفحات. كل شاشة ملف HTML مستقل، بعكس Single-Page Application اللي بيكون فيه ملف واحد والتنقل داخلي.

فكرة البناء الأساسية

كل صفحة داخلية عبارة عن قشرة فارغة: ملف HTML ما فيه إلا <div id="app-shell"></div> وسطر يستدعي ملف JavaScript. كل الواجهة تُرسم من JavaScript. هذا يسمى Client-Side Rendering — المتصفح هو اللي يبني الصفحة، مش الخادم.

dashboard.html → <div id="app-shell"></div> → <script type="module" src="js/dashboard.js"> js/dashboard.js → initPage("dashboard") // يرسم الهيكل المشترك → loadDashboard() // يرسم محتوى الصفحة

تقسيم الملفات (Separation of Concerns)

كل ملف له مسؤولية واحدة واضحة — هذا المبدأ اسمه Separation of Concerns (فصل الاهتمامات):

كيف أشرحها شفهيًا؟

«النظام مبني كـ Multi-Page Application بـ Vanilla JavaScript باستخدام ES Modules. كل صفحة HTML هي قشرة فارغة، والمحتوى يُرسم بالكامل من JavaScript — أي Client-Side Rendering. طبّقت مبدأ Separation of Concerns: طبقة للوصول للبيانات، طبقة للتخزين، طبقة منطق صافي للتحقق والحسابات، وطبقة مكوّنات واجهة قابلة لإعادة الاستخدام.»

٢ · Main Technologies & Features Used

هذه التقنيات مستعملة فعليًا في المشروع. ما فيه React ولا قاعدة بيانات ولا خادم خلفي.

Vanilla JavaScript (ES Modules)

وظيفتها: لغة البرمجة الأساسية، بلا أي إطار عمل. وين: كل ملفات js/. ليش: المشروع بحجم يسمح ببنائه بلا إطار، وهذا يخلّي المنطق مكشوفًا وسهل الشرح. مثال: import { getPatients } from "./api.js" — نظام ES Modules يخلي كل ملف يصدّر دواله ويستوردها غيره.

Tailwind CSS (Play CDN)

وظيفتها: إطار CSS قائم على Utility Classes — كلاسات صغيرة كل وحدة تعمل شيئًا واحدًا (p-4 = padding، flex = display flex). وين: كل ملفات HTML وكل HTML مولّد من JavaScript. ليش: تسريع بناء الواجهة بلا كتابة CSS مخصص لكل عنصر.

Tailwind Configuration — الهوية بلا أي ملف CSS

وظيفتها: Tailwind من الـCDN يبني الستايل وقت التحميل من كائن tailwind.config. فبدل كتابة CSS، عرّفنا لوحة الألوان والحركات كـJavaScript. وين: js/tailwind-theme.js. ليش: المشروع خالٍ تمامًا من ملفات CSS — كل التنسيق إما كلاسات Tailwind أو خصائص نكتبها من JavaScript.

وكيف يشتغل الـDark Mode بلا CSS؟ بدل ما نضيف dark: على مئات العناصر، نقلب المقياس المحايد نفسه: slate-50 (خلفية الصفحة) تصير غامقة، وslate-900 (لون النص) يصير فاتحًا. الكلاسات في الصفحات لا تتغير أبدًا — تتغير القيم وراءها فقط. ولأن Tailwind يولّد ستايله مرة واحدة عند التحميل، تبديل الوضع يحفظ التفضيل ويعيد تحميل الصفحة.

localStorage (Web Storage API)

وظيفتها: تخزين دائم في المتصفح يبقى بعد إغلاق الصفحة. وين: js/storage.js — كل مفاتيحه تبدأ بـcardiac. ليش: ملفات JSON للقراءة فقط، فأي شيء يضيفه الطاقم يُحفظ هنا. مثال: cardiac.appointments · cardiac.vitals · cardiac.activity

Fetch API + JSON

وظيفتها: قراءة ملفات البيانات بشكل غير متزامن (Asynchronous). وين: fetchJson() في js/api.js. ليش: ملفات data/*.json تلعب دور قاعدة البيانات الأولية. مثال: await fetch("./data/patients.json") — وCaching بسيط عبر Map يمنع إعادة الطلب في نفس الصفحة.

Custom Events (Event-Driven Updates)

وظيفتها: إشارة تنطلق عند أي تغيير في البيانات فتعيد الشاشات رسم أرقامها. وين: dataChangedEvent وonDataChange() في storage.js. ليش: بديل بسيط عن State Management Library. مثال: إضافة موعد ← إشارة ← بطاقات لوحة التحكم تتحدث بلا إعادة تحميل. وحدث storage يوصّل التغيير حتى بين تبويبين مفتوحين.

IntersectionObserver + MutationObserver

وظيفتها: الأولى تكشف وصول العنصر للشاشة (Scroll Reveal)، والثانية تكشف إضافة عناصر جديدة للصفحة. وين: js/animations.js. ليش: المحتوى يُرسم من JavaScript، فنحتاج مراقبة العناصر الجديدة تلقائيًا.

Lucide Icons · Google Fonts (Cairo)

وظيفتها: مكتبة أيقونات SVG، وخط عربي واضح. وين: icon() في ui.js، والخط في رأس كل صفحة.

تنويه مهم للمناقشة: ما هو غير موجود

لا يوجد Backend Server ولا Database (لا SQL ولا Firebase)، ولا مكتبة رسوم بيانية (الرسوم مبنية بـCSS بعرض شريط يساوي النسبة المئوية)، ولا Authentication حقيقي بكلمة مرور — صفحة الدخول اختيار دور يُحفظ في localStorage. لكن يوجد Authorization فعلي: كل صفحة تتحقق من الدور وترفض الدخول غير المصرّح. اذكر هذا بصراحة — يبيّن أنك تعرف الفرق بين Authentication وAuthorization.

٣ · Data Flow — تدفق البيانات

المسار عند القراءة (Read)

data/*.json ──fetch──► api.js │ localStorage ──────────────►│ MERGE ▼ getPatients() / getAppointmentsWithPatients() / getVitalRecords() ▼ Feature Module (dashboard.js …) ──► ui.js ──► DOM

api.js هو نقطة الدمج: يقرأ الملف الأصلي، ويطبّق فوقه ما حفظه الطاقم (patientUpdates وstatusOverrides)، فيرجع نسخة موحّدة. هذا يسمى Data Transformation.

المسار عند الكتابة (Write)

1. User Input (Form) ▼ 2. Client-Side Validation ← helpers.js validateAppointment() / validateVitalRecord() ▼ 3. Domain Rules Layer ← appointment-rules.js conflict check against live data ▼ 4. Storage Layer ← storage.js final guard + write to localStorage ▼ 5. Emit Change Event ← dataChangedEvent ▼ 6. Re-render subscribers ├─ Dashboard cards ├─ Tables ├─ Reports charts ├─ Notifications bell └─ Recent Patients

بالعربي: مُدخلات المستخدم تمر بالتحقق، ثم بطبقة القواعد التي تفحص التعارض على أحدث نسخة من البيانات، ثم بطبقة التخزين التي فيها حارس أخير قبل الكتابة. بعدها تُطلق إشارة التغيير فتعيد كل الشاشات المشتركة حساب أرقامها ورسمها — بطاقات لوحة التحكم والجداول والتقارير وجرس الإشعارات وقسم أحدث المرضى.

كيف أشرحها شفهيًا؟

«عند إضافة موعد: البيانات تمر بـValidation، ثم بطبقة قواعد تفحص التعارض على أحدث نسخة من البيانات، ثم تُكتب في التخزين. بعد الكتابة نطلق Custom Event، وكل شاشة مشتركة عليها Listener تعيد حساب أرقامها. لذلك لوحة التحكم والتقارير والإشعارات تتحدث تلقائيًا بلا إعادة تحميل الصفحة.»

الفرق بين الأدوار في جملة

  • الطبيب: الوحيد الذي يعتمد حالة المريض، ويحذف القراءات، ويرى التقارير الإدارية.
  • الممرضة: تسجّل القراءات والملاحظات التمريضية، لكن لا تعتمد الحالة ولا تحذف قراءات زميلاتها.
  • موظف الاستقبال: الوحيد الذي يسجّل مريضًا جديدًا، ولا يرى أي بيانات سريرية إطلاقًا.

كيف أشرحها شفهيًا؟

«الـAuthorization مطبّق على ثلاث طبقات: Route Guard يمنع فتح الصفحة أصلًا، ثم Navigation Filtering يخفي الرابط، ثم Conditional Rendering يخفي الأزرار داخل الصفحة. والمهم أن الحماية ليست في الواجهة فقط — دالة canEditRecord مثلًا تُستدعى مرة عند رسم الزر ومرة ثانية عند الحفظ.»

Today's Appointments — مواعيد اليوم

Recent Patients — أحدث المرضى

الهدف: ليس أحدث المسجّلين، بل آخر المرضى الذين حدث تحديث على ملفهم: تسجيل قراءة، تعديل بيانات، تغيّر حالة، ملاحظة جديدة، أو موعد.

مصدر وقت التحديث: لم نخترع نظام تتبّع جديد — استعملنا Activity Log الموجود أصلًا، حيث تُكتب كل عملية مع createdAt. الإضافة الوحيدة أن كل إجراء صار يحمل patientId صريحًا ليمكن التجميع حسب المريض.

getRecentlyUpdatedPatients(patients, activityLog, limit) 1. GROUPING → last action per patientId (from activity log) 2. FALLBACK → no action yet ? use patient.lastReadingAt 3. SORTING → descending by update time (Date.parse) 4. SLICING → take first 6

بالعربي: نجمّع آخر إجراء لكل مريض من سجل الإجراءات، والمريض الذي لا إجراء له نأخذ وقت قراءته المرجعية، ثم نرتّب تنازليًا حسب وقت التحديث ونأخذ أول ستة.

ملاحظة تقنية: أوقات سجل الإجراءات بصيغة UTC وأوقات ملف البيانات محلية، فلا نقارن النصوص مباشرة — بل نحوّل الاثنين إلى أرقام عبر Date.parse() ثم نقارن. الدالة getRecentlyUpdatedPatients() في helpers.js.

«قسم Recent Patients يعتمد على Sorting بآخر وقت تحديث. مصدر الوقت هو الـActivity Log الذي يسجّل كل عملية مع وقتها ورقم المريض. أعمل Grouping لأخذ آخر إجراء لكل مريض، ثم Sort تنازلي، ثم Slice لأول ستة. لذلك أي تحديث ينقل المريض لأعلى القائمة فورًا.»

٧ · Blood Pressure — من الإدخال حتى الحفظ

ضغط الدم أهم مثال على Input Validation في المشروع، لأنه قيمتان في حقل نصي واحد.

١. الإدخال (Input)

حقل واحد type="text" — ليس type="number" لأن الرقمي لا يقبل الشرطة المائلة ويُظهر عدّادًا. التلميح 120/80 موضوع كـ placeholder وليس value — فرق جوهري:

  • • placeholder: نص خافت يختفي فور الكتابة، ولا يُرسل مع النموذج.
  • • value: قيمة فعلية تُحفظ — لو استعملناها لحُفظ 120/80 لكل مريض لم يُدخل شيئًا.

٢. التحقق (Validation) — أربع خطوات مرتّبة

getBloodPressureError(value) 1 · FORMAT bloodPressurePattern.test(value) // Regex Validation /^\d{2,3}\/\d{2,3}$/ 2 · PARSING splitBloodPressure(value) // "120/80" ⇒ {systolic, diastolic} 3 · RANGES getSystolicError() / getDiastolicError() MIN_SYSTOLIC 50 … MAX_SYSTOLIC 260 MIN_DIASTOLIC 30 … MAX_DIASTOLIC 160 4 · RELATIONSHIP getBloodPressureOrderError() systolic > diastolic

لماذا هذا الترتيب؟ لأن كل خطوة تفترض نجاح ما قبلها: لا معنى لفحص المدى قبل التأكد أن القيمة رقم. هذا يسمى Fail Fast — نتوقف عند أول خطأ ونعرض رسالته.

القيمة تُحفظ كنص "120/80" — نفس صيغة data/patients.json. هذا Data Consistency: المصدران يتّحدان في الصيغة فيقرأهما نفس الكود.

وقبل الكتابة يوجد حارس أخير في storage.js: assertValidVitalValues() ترمي خطأ إذا كانت القيمة غير صالحة — حتى لو استُدعيت الدالة مباشرة من console المتصفح.

٥. الحدود في مكان واحد (Constants)

كل الأرقام معرّفة مرة واحدة في helpers.js ولا تتكرر داخل الشاشات:

export const systolicLimits = { min: 50, max: 260 }; // MIN/MAX_SYSTOLIC export const diastolicLimits = { min: 30, max: 160 }; // MIN/MAX_DIASTOLIC export const heartRateLimits = { min: 20, max: 220 }; export const oxygenLimits = { min: 60, max: 100 };

تعديل الحد يتم من سطر واحد فينعكس على النموذج ولوحة التعديل وحارس التخزين معًا. الهدف سلامة البيانات لا التشخيص — النظام لا يحكم على حالة المريض من رقم واحد.

كيف أشرحها شفهيًا؟

«ضغط الدم يُدخَل في حقل نصي واحد بصيغة 120/80. أبدأ بـRegex Validation للتأكد من الصيغة، ثم Parsing لفصل النص إلى قيمتين، ثم أحوّلهما إلى أرقام وأفحص كل واحدة ضمن مداها المسموح، وأخيرًا أفحص العلاقة بينهما. الحدود معرّفة كـConstants في مكان واحد. والقيمة تُحفظ كنص بنفس صيغة ملف البيانات لضمان Data Consistency.»

منع الموعد في الماضي — أربع طبقات

Layer 1 · HTML attribute min="today" visual hint only Layer 2 · Form Validation validateAppointment() message under the field Layer 3 · Domain Rules appointment-rules.js checked against live data Layer 4 · Storage Guard storage.js throws — even from console

بالعربي: الطبقة الأولى إرشاد بصري فقط، الثانية تعرض الرسالة تحت الحقل، الثالثة تفحص قبل الحفظ على أحدث بيانات، والرابعة ترفض الكتابة نهائيًا حتى لو استُدعيت الدالة مباشرة من console المتصفح.

لماذا أربع طبقات؟ لأن الطبقة الأولى يمكن تجاوزها بحذف الخاصية من أدوات المطوّر. الحماية الحقيقية في الطبقات ٢–٤. هذا مبدأ Defense in Depth.

منع التعارض — Conflict Detection

كل موعد فترة زمنية وليس نقطة: يبدأ في وقته وينتهي بعد ٣٠ دقيقة. فترتان تتعارضان إذا:

first.start < second.end && second.start < first.end

قاعدة الحجز: نفس المريض لا يكون له موعدان متداخلان، ونفس الطبيب لا يستقبل موعدين في نفس الفترة. الموعد المكتمل لا يحجز وقتًا. لذلك 10:00 و10:15 يتعارضان، بينما 10:00 و10:30 لا يتعارضان.

حالة مريم حسن — لماذا لا يظهر «سابق»؟

موعد مريم حسن بتاريخ ١٦ أغسطس وحالته «مكتمل». القاعدة في الكود:

const isPastRow = !isUpcomingAppointment(appointment) && appointment.status !== appointmentStatuses.completed;

أي أن وسم «سابق» يظهر فقط للموعد الذي فات ولم يُكتمل. الموعد المكتمل يعرض شارة «مكتمل» في عمود الحالة، وإضافة «سابق» بجانبها تكرار بلا فائدة.

هذا سلوك مقصود وصحيح، ولم يُغيَّر. وقد بدا استثنائيًا لسبب بسيط: موعد مريم هو الموعد المكتمل الوحيد في ملف البيانات كله — التسعة الباقية حالتها «مجدول» أو «عاجل» وتواريخها فاتت، فكلها تعرض «سابق».

أولوية العرض: مكتمل ← «مكتمل» · قادم ← بلا وسم · فات ولم يكتمل ← «سابق».

«وسم Past مشتق (Derived) وليس مخزّنًا: يُحسب من التاريخ والوقت وحالة الموعد معًا. وحالة الموعد الفعلية لها أولوية أعلى في العرض — فالموعد المكتمل يعرض Completed لأن إضافة Past بجانبه تكرار. موعد مريم هو الموعد المكتمل الوحيد في البيانات، ولذلك بدا مختلفًا.»

١٢ · البحث والفلترة والجداول

كيف تعمل الفلترة؟

كل صفحة فيها كائن filters يمثّل UI State. الدورة كالتالي:

User types / selects ▼ Event Handler updates the `filters` object ← State Update ▼ getVisible…() applies the filters ← Filtering (Pure Function) ▼ render…() redraws the table ← Re-render

نقطة مهمة: الفلترة لا تحذف أي بيانات — المصفوفة الأصلية allPatients تبقى كاملة، وfilter() ترجع مصفوفة جديدة للعرض فقط. لذلك «إلغاء التصفية» يعيد كل الصفوف فورًا.

  • • الملاحظات: الأحدث أولًا
  • • أحدث المرضى: بآخر وقت تحديث
  • • توزيع التشخيصات: تنازليًا حسب عدد المرضى

Pagination

لا يوجد Pagination في المشروع. بدلًا منه نستعمل .slice() لتحديد عدد العناصر في القوائم المختصرة (أحدث ٦ مرضى، أقرب ٦ مواعيد). عدد المرضى الحالي لا يستدعي تقسيم صفحات. لا تدّعِ وجودها في المناقشة.

ثلاثة أنواع من التنبيهات

buildAlerts() في layout.js تجمع:

  1. ١. تنبيهات الحالات الحرجة — محسوبة من البيانات، وتظهر للطبيب والممرضة فقط.
  2. ٢. تنبيهات المواعيد العاجلة — المواعيد القادمة ذات الحالة «عاجل».
  3. ٣. إجراءات الزملاء — من سجل الإجراءات، وتصل للأدوار الثلاثة.

المقروء وغير المقروء

كل دور له قائمة مقروءاته المنفصلة — المفتاح cardiac.readAlerts.{الدور}. فقراءة الطبيب للإشعار لا تخفيه عن الممرضة. والعدّاد الأحمر يعرض غير المقروء فقط.

التحديث الفوري: onDataChange(() => loadAlerts()) — أي عملية تحدّث الجرس فورًا، حتى لو نُفّذت من تبويب آخر مفتوح.

«الإشعارات Event-Driven: بعد نجاح أي عملية نستدعي addActivity التي تكتب سجلًا يحتوي ماذا حدث ومن نفّذه ومتى ولأي مريض ولمن يجب أن يصل. الجرس يقرأ من هذا السجل ويفلتره حسب دور المستخدم. وحالة القراءة مخزّنة لكل دور على حدة، فقراءة أحدهم لا تؤثر على الآخرين.»

الحركات (Animations)

كل الحركات على transform وopacity فقط، لأنهما الخاصيتان اللتان يعالجهما المتصفح بكفاءة بلا إعادة حساب التخطيط. الطرق المستعملة:

  • • Scroll Reveal — IntersectionObserver يضيف كلاس عند وصول العنصر للشاشة.
  • • Card Hover / Tilt — مستمع واحد على مستوى الصفحة (Event Delegation) يمرّر موقع الماوس كمتغيرات CSS.
  • • Staggered Entrance — تأخير متدرّج فتدخل العناصر ورا بعض.

احترام تفضيلات المستخدم: prefers-reduced-motion يوقف كل الحركات لمن فعّل «تقليل الحركة» في نظامه — نقطة Accessibility. والأجهزة بلا ماوس لا تُشغَّل عليها حركات المرور أصلًا.
